# Anchor program specification | canonical V1.3
One Rust Anchor program, one fixed legacy SPL mint (6 decimals), test only. All integer amounts in base units, u64 with checked math (u128 intermediate). Fixed 2000 basis points. Pin mutually compatible CLI/crates/TS client after H02; no guessed versions. IDL generated by actual build. Anchor account validation plus explicit checks. Canonical seeds byte literals; pubkeys 32 bytes; asset_id and order_id and bounty_id each random 16 bytes; version u32 LE. PDA derivation includes program ID. All struct sizes below exclude 8-byte Anchor discriminator; allocate using InitSpace or exact measured IDL serialization + discriminator. Never reuse closed receipt/state account IDs.

## Accounts
| Account | Seeds | Fields (Borsh fixed width) | Authority / invariants |
|---|---|---|---|
| Config | ["config"] | admin pubkey, mint pubkey, treasury pubkey, fee_bps u16, bump u8 | initialize only by deployment authority fixed at build/deploy or verified upgrade authority; no arbitrary first caller; immutable thereafter |
| DataAsset | ["asset", provider, asset_id, version_le] | provider pubkey, asset_id [16], version u32, content_hash [32], license_hash [32], price u64, active bool, bump u8 | provider signer; immutable terms, toggle active only |
| PurchaseReceipt | ["receipt", buyer, order_id, asset PDA] | buyer, provider, asset, mint pubkeys; order_id [16], version u32, content_hash [32], license_hash [32], amount u64, provider_amount u64, platform_amount u64, timestamp i64, kind u8 (0 purchase,1 bounty), bump u8 | init once, never close/edit; payer buyer/requester. 254 bytes total incl discriminator (verify actual layout). |
| Bounty | ["bounty", requester, bounty_id] | requester pubkey, bounty_id [16], requirement_hash [32], reward u64, deadline i64, status u8 (0 open,1 accepted,2 refunded), winner_submission pubkey (zero until accepted), bump u8 | terminal state immutable; no close, ID permanent |
| Submission | ["submission", bounty, provider, asset] | bounty, provider, asset pubkeys, bump u8 | submitter signs, immutable, no close |
| Vault | associated token account of Bounty PDA for Config.mint | standard legacy token account | owner authority Bounty PDA; only program CPI signs; exact ATA checked |

Receipt size calculation: 4×32+16+4+32+32+4×8+1+1+8 = 254 bytes (authoritative computed size; use code-generated size). Do not rely on hand estimates. Domain order IDs are random 16 bytes for purchases; bounty receipt order_id = bounty_id; to prevent colliding purchase/order namespace, bounty receipt uses separate prefix `b"bounty_receipt"` with seeds [prefix, bounty PDA, asset PDA]; fields buyer=requester, kind=1. Use these prefixes in verifier.

## Common invariants
Config PDA, expected program ID and legacy Token Program exact ID, mint owner and decimals, signer ownership, derived PDA seeds/bump. Token accounts must be canonical associated token accounts for expected wallet and mint (precreate all ATAs before purchase; check owner/mint and address). Treasury must not alias buyer/provider; reject buyer=provider, requester=provider and provider=treasury in demo. No Token-2022 extensions, delegated spender, arbitrary token accounts or arbitrary CPIs. No keys in repo or API response. Check nonzero price/reward, bounded integer conversion, no zero provider share. Use Clock.unix_timestamp on-chain, not browser. Check nonzero hashes. All instructions validate before transfers; CPI TransferChecked with config mint decimals, no arbitrary programs. No close receipt, no reinitialize config. Program upgrade authority is a demo trust assumption, record public key; production review later.

## Instructions (account order may follow generated IDL, semantics fixed)
1. `initialize_config(mint, treasury)` — authorized deployer signer, payer, Config init, legacy Mint, system program. Reject mint decimals !=6, treasury default/authority mismatch. Hardcode fee=2000. Reinitialization fails. Document how initializer is pinned (compile-time public key or checked loader upgrade authority), prove unauthorized initializer test.
2. `register_data_asset(asset_id,version,content_hash,license_hash,price,active)` — provider signer/payer, config, asset init, system program. Price>0 and hashes nonzero, version>=1. Only provider defines version. No update of terms; new version registers new PDA; use inactive for bounty solution. Body existence is off-chain preflight, not a chain guarantee.
3. `set_asset_active(active)` — provider signer, asset mut; verify provider, seeds. No other fields change. Past receipts unaffected. UI calls deactivate/activate via this instruction.
4. `purchase_unit(order_id,expected_price,expected_content_hash,expected_license_hash,expires_at)` — buyer signer/payer, config, asset, receipt init, buyer ATA mut, provider ATA mut, treasury ATA mut, mint, Token Program, system program. Verify active, terms match signed expected fields and deadline (now < expires_at), buyer funds, canonical accounts, no alias. Transfer provider share then fee (skip zero fee); write receipt. Version is bound by asset PDA; no update. Client constructs a transaction with TWO such instructions sharing buyer/order_id, distinct assets and providers, no unrelated instructions. Both succeed or both roll back including receipts (network fee may still be charged). Not a single dynamic batch instruction; atomicity is Solana transaction-level. Program permits standalone purchase_unit; API does not describe it as a full bundle. Signed tx binds exact price per item, buyer budget enforced by client sum (not global on-chain budget). At least two real providers required. Precreate ATAs, measure serialized bytes<=1232 and simulation compute, omit extra memo, use one signer/fee payer. If two still exceed size, use v0+ALT only after tested; do not silently split the bundle. Third item optional only if full tx fits.
5. `create_bounty(bounty_id,requirement_hash,reward,deadline)` — requester signer/payer, Config, Bounty init, requester ATA, vault ATA owned by Bounty PDA (create idempotently if absent; validate canonical ATA if already present), mint, legacy token/ATA/system programs. Verify now<deadline, max deadline demo 7 days, reward>0, hash nonzero. Transfer full reward requester→vault; set OPEN. No fee now.
6. `submit_bounty_solution()` — provider signer/payer, bounty, asset, submission init, system program. Check OPEN and now<deadline; asset.provider==signer, asset inactive at submission, provider != requester/treasury. Store reference; no token movements. One immutable submission per bounty/provider/asset; multiple submissions permitted. Asset content/license immutable. Off-chain requester reviews exact hash and deterministic fields; no quality oracle.
7. `accept_bounty_solution(expected_requirement_hash,expected_content_hash,expected_license_hash)` — requester signer/payer, config, bounty mut, submission, asset, vault mut, provider ATA mut, treasury ATA mut, mint, bounty receipt init, system/token programs. Check OPEN, now<deadline, requester, submission.bounty==bounty, asset==submission.asset, provider match, expected hashes, canonical vault and recipient ATAs. Pay exactly reward split with Bounty signer seeds, create bounty receipt (buyer=requester), winner=submission, status ACCEPTED. Vault may receive unsolicited tokens: do not require balance==reward; transfer exactly reward; leave surplus in vault in demo (no arbitrary sweep), report residual. Never release twice. Receipt grants review/purchase entitlement even if asset inactive. Provider may activate after acceptance. Keep vault and bounty accounts for audit; no close/sweep in demo. No fee on unsolicited funds.
8. `refund_expired_bounty()` — requester signer, config, bounty mut, vault mut, requester ATA mut, mint, Token Program. OPEN, now>=deadline, same requester and canonical ATA, transfer exactly funded reward to requester using PDA authority, status REFUNDED, winner remains zero. Surplus remains as above. No receipt and no commission. Competing accept/refund serialized by writable Bounty, exclusive timestamp boundaries. No early cancel, no dispute arbitrator. A requester can refuse honest work; provider risk disclosed.

## State / error vocabulary
Asset ACTIVE ↔ INACTIVE (provider only); immutable receipt exists or not; bounty OPEN → ACCEPTED or REFUNDED, terminal states no outgoing. Errors: UnauthorizedInitializer, Unauthorized, InvalidMint, InvalidTokenAccount, InvalidTerms, InactiveAsset, InvalidPrice, ExpiredQuote, DuplicateReceipt (Anchor init may return framework error), InsufficientFunds, ArithmeticOverflow, InvalidDeadline, InvalidSubmission, BountyNotOpen, DeadlinePassed, DeadlineNotReached, HashMismatch. Map framework errors without losing original logs. No claim these codes are actual IDL until implementation.

## Delivery trust boundary
Finalized receipt owner must equal configured program, exact PDA recomputation, expected mint/kind/buyer/asset/version/hashes/amount and original immutable bytes. Signed wallet challenge binds action, receipt, nonce, expiry and domain; no signature = no bytes. Transaction signature alone cannot authorize data. On-chain atomic payment is not atomic off-chain delivery; retry idempotently; retain original bytes; if missing, mark delivery failure and no fake success. No purchase refunds in program; real commercial remedy deferred. Hash proves match to registered bytes, not truth, ownership, readership, license validity, or future compliance. Public hashes can reveal low-entropy data via guessing; synthetic data only; no personal/sensitive metadata on chain.
