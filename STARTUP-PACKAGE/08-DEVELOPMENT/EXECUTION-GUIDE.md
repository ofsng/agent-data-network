# Single-session development guide
1. Inspect git, PROJECT-STATE, existing tests/IDL/fixtures; preserve user changes and evidence. Confirm official contest rules. No redundant code generation. Reuse pinned package manager/Anchor versions and installed Solana skill/MCP; only install missing official dependencies. Do not wait for external accounts.
2. Establish isolated local validator, disposable keys, test mint, ATAs and chain config. Build/verify actual program. If local validator works, avoid Devnet until demo is complete. Do not alter original ABI unless a verified bug requires it; record compatibility impact. Check actual transaction serialization and simulation. Two-unit bundle must be one transaction.
3. Seed original immutable bytes with trust sidecar; snapshot exact bytes. Use actual chain to register, query, quote, settle and verify. Implement bounded wallet proof, recovery, and durable spend guard, then deterministic tool driver. Test negative cases close to code.
4. Implement bounty creation, submission, bounded review, acceptance, separate refund and resale. Respect independent budgets and states. No full answer before accept through runtime API. Preserve limitations.
5. Connect single guided browser UI to existing services (DEMO-EXPERIENCE). Build reusable steps, runtime badge, actual tool trace and evidence drawer. Use one loopback process and no arbitrary signing endpoint. No new production UI framework; focus on coherent visual hierarchy, state and responsiveness.
6. Rehearse full flow twice; test rollback, unauthorized delivery, expiry/refund, stale/duplicate/overbudget, corruption/recovery and UI reset. Produce evidence manifest from actual results. Record local vs Devnet vs simulation; no false PASS. Check lint/build and secret files; exact launch commands. Optional live MCP/model or x402 only if core verified and time permits.
7. Freeze, update PROJECT-STATE and README, export demo screenshots or recording if tooling available. No claim of actual submission. Do not deploy to mainnet, provision cloud, buy credits, request unnecessary approval or restart from scratch. If blocker persists, deliver usable isolated demo with clear technical gap.
## Environment
Use existing local stack; configuration example: DEMO_MODE=LOCAL_CHAIN, RPC_URL=http://127.0.0.1:8899, PROGRAM_ID=<actual>, MINT=<actual>, DEMO_DATA_DIR=<ignored isolated path>, RUN_TOKEN=<local generated>, PORT=<free port>. Separate test mode from existing data; keys not in git/browser. Setup/reset must only touch demo namespace. No external service secrets. Never commit real private keys or fixture expected answers to public endpoint.
## Completion
Use task specs, test matrix, demo experience and actual evidence. Record each task PASS/FAIL/BLOCKED/NOT RUN (optional omitted); no documentation-only completion claims. Technical gate and UX gate separate.
